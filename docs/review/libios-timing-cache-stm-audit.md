# IOS timing, cache, and STM audit

Reviewer: `/root/reviewer_6`  
Scope: independent source audit of the remaining timing, cache, and STM questions in `docs/review/libios.md`. The preferred-version zero-size TMD fix is excluded.

## Confirmed mismatches

- **Launch polling delay:** C waits for the version word with `udelay(1000)` after each unsuccessful read (`../../C-sources/libogc/libogc/ios.c:290-291`). Its IPC readiness loop also calls `udelay(1000)` before each register check (`ios.c:307-312`). `udelay` measures elapsed time from `gettime()` until at least the requested microseconds have passed (`../../C-sources/libogc/libogc/timesupp.c:66-77`). Rust instead executes a fixed number of `core::hint::spin_loop()` calls: 1024 iterations per failed version check and 4096 before each IPC check (`crates/core/ogc-ios-sys/src/lib.rs:93-99,138-146`). This does not enforce a 1000 microsecond minimum or a time-based delay. The polling cadence and elapsed launch timing therefore differ statically from C.
- **STM initialization failure behavior:** C `__STM_Init` returns `0` when either `IOS_Open` fails, regardless of the negative open error (`../../C-sources/libogc/libogc/stm.c:87-92`). The caller treats only negative results as errors (`../../C-sources/libogc/libogc/ios.c:81-87`), so this STM failure does not replace the subsystem return value. Rust `stm_init_powerpc` returns the negative `open_file` error when opening either STM device fails (`crates/core/ogc-ios-sys/src/lib.rs:166-191`); `_ios_initialize_subsystems` then treats it as an error and lets it replace an earlier ES error (`lib.rs:302-309`). This changes both the returned result and error precedence.
- **Event-hook lifecycle omitted by the IOS wrapper:** C `__STM_Init` calls `__STM_SetEventHook` after setting STM initialized (`../../C-sources/libogc/libogc/stm.c:98-100`); that function sends `IOCTL_STM_EVENTHOOK` on the eventhook descriptor (`stm.c:123-138`). C shutdown calls `__STM_ReleaseEventHook` before closing either descriptor (`stm.c:103-108`), which sends `IOCTL_STM_RELEASE_EH` when registered (`stm.c:141-153`). Rust's IOS wrapper only opens and stores the two descriptors (`crates/core/ogc-ios-sys/src/lib.rs:166-191`) and then closes them in `stm_close_powerpc` (`lib.rs:195-218`); it does not install or release the event hook. Although the separate `ogc-stm` crate implements these operations, the IOS wrapper path does not call its `init` or `close` functions.
- **Partial-open cleanup/order:** If C opens `/dev/stm/immediate` but fails to open `/dev/stm/eventhook`, it returns without closing or clearing the immediate descriptor (`stm.c:87-92`). `__STM_Close` later attempts to close that stored descriptor (`stm.c:103-120`). Rust closes the immediate descriptor immediately after the eventhook open fails, and returns the eventhook error; it retains the immediate descriptor only if that close itself fails (`crates/core/ogc-ios-sys/src/lib.rs:173-185`). The observable close timing and failure handling differ. C's eventual `__STM_Close` also always calls `__STM_ReleaseEventHook` before closing descriptors, including after an unsuccessful initialization (`stm.c:103-108`); Rust's `stm_close_powerpc` only closes descriptors and does not issue a release ioctl (`crates/core/ogc-ios-sys/src/lib.rs:195-218`).

## Cache behavior compared

- **No invalidation-range mismatch confirmed for the version address.** C `IOS_GetVersion` and `IOS_GetRevision` invalidate eight bytes at `0x80003140` before reading a word (`../../C-sources/libogc/libogc/ios.c:185-204`). `PPCDCacheInvalidate` rounds the start down to a cache-line boundary and computes all intersecting lines (`../../C-sources/libogc/tuxedo/cache.c:8-23,29`). The address is 32-byte aligned and the eight-byte range remains within one line. Rust invalidates that address with one `dcbi` and then executes `sync` before its volatile word load (`crates/core/ogc-ios-sys/src/lib.rs:63-75`). Both invalidate the one containing line; Rust adds an ordering instruction. C launch polling itself uses `read32` without cache invalidation (`ios.c:290`), while Rust's helper invalidates the line on each poll. The effect of this extra invalidation in the launch loop is not classified as a mismatch from source alone.

## Independent re-review — timing and STM findings

Result: **NEEDS_CHANGES** for the recorded timing and STM scope.

Reviewer: `/root/reviewer_d`. Implementer: the Rust implementation under review originated in commits `b2db513` (launch path), `f20cc9c` (STM path), and `d87d3c5` (subsystem result handling), authored as `notOrrytrout`; later STM cleanup behavior is in `45b3ca8`. No new implementation was made in this review. I checked current Rust against C `ios.c`, `timesupp.c`, and `stm.c` directly.

### Re-verified confirmed mismatches

- **Launch polling is iteration based in Rust and time based in C.** C checks the IOS version word at `ios.c:290` and calls `udelay(1000)` after each failed read (`ios.c:290-291`). `udelay` waits until `diff_usec(start, end) >= us` using `gettime()` (`timesupp.c:66-77`). C also delays 1000 microseconds before every IPC control check (`ios.c:307-312`). Rust checks `ios_read_version_word()` and then runs 1024 `spin_loop()` iterations (`crates/core/ogc-ios-sys/src/lib.rs:93-99,138-140`); before each IPC check it runs 4096 iterations (`lib.rs:142-147`). These loops do not enforce the C elapsed-time minimum or cadence. The IPC retry count and check-after-delay order otherwise correspond.
- **STM open errors and subsystem error precedence differ.** C `__STM_Init` returns zero on either failed `IOS_Open` (`stm.c:87-92`). `__IOS_InitializeSubsystems` only treats negative subsystem results as errors and stores the ES error first, then overwrites it only if STM returns a negative value (`ios.c:67-91`). Rust returns the negative IPC `open_file` error on either STM open failure (`crates/core/ogc-ios-sys/src/lib.rs:173-187`) and `initialization_result` lets any negative STM result replace an earlier ES error (`ios_logic.rs:10-19`, called at `lib.rs:302-309`). Thus the Rust wrapper exposes an STM open failure and may report it instead of an earlier ES failure where C returns the ES result.
- **The IOS STM path omits event-hook registration and release.** C calls `__STM_SetEventHook` after setting initialized (`stm.c:98-100`); the registration issues `IOS_IoctlAsync` with `IOCTL_STM_EVENTHOOK` (`stm.c:123-138`). Shutdown calls `__STM_ReleaseEventHook` before closing descriptors (`stm.c:103-120`); release sends `IOCTL_STM_RELEASE_EH` on the immediate descriptor when a handler is registered (`stm.c:141-153`). Rust `stm_init_powerpc` only opens and stores the two file descriptors (`crates/core/ogc-ios-sys/src/lib.rs:166-191`), and `stm_close_powerpc` only closes them (`lib.rs:195-218`). The separate `ogc-stm` crate does not get invoked by these IOS wrapper functions. This is a confirmed difference in the `ogc-ios` subsystem lifecycle.
- **Failed second-open cleanup occurs at a different time and has different state.** When C opens the immediate descriptor but event-hook open fails, `__STM_Init` returns zero and leaves the immediate descriptor stored (`stm.c:87-92`); later `__STM_Close` attempts release first, then closes and clears the stored descriptors (`stm.c:103-120`). Rust explicitly closes the immediate descriptor as soon as the event-hook open fails, returns the event-hook error, and retains the immediate fd only if that close fails (`crates/core/ogc-ios-sys/src/lib.rs:177-186`). The descriptor lifetime, return value, and eventual close/release flow differ. On ordinary close, Rust also preserves a descriptor after close failure for a later retry (`lib.rs:198-215`), while C clears the stored fd after each close attempt (`stm.c:109-117`); this is a deliberate retry/safety behavior but is not C state parity.

### Additional launch ordering difference

C reinstalls and unmasks the ACR interrupt before `__IPC_Reinitialize` and the post-launch version query (`ios.c:318-325`). Rust calls `ogc_ipc::reinitialize()` before requesting and unmasking the handler, and does so only after the version query (`crates/core/ogc-ios-sys/src/lib.rs:142-159`). This changes interrupt availability during reinitialization and version validation. Both paths restore the handler on version mismatch, but they do so at different points.

### Cache behavior and validation

The existing cache conclusion remains: C invalidates the eight-byte version range through `PPCDCacheInvalidate` (`ios.c:185-204`; cache helper rounds to the containing line in `../../C-sources/libogc/tuxedo/cache.c:8-23,29`), while Rust invalidates the aligned version address with `dcbi` and `sync` before the volatile read (`crates/core/ogc-ios-sys/src/lib.rs:60-75`). The launch loop consequently adds invalidation on each Rust poll where C only performs `read32` (`ios.c:290`). I still classify the effect of that extra invalidation as uncertain from source alone.

`cargo check -p ogc-ios -p ogc-ios-sys --tests --target powerpc-unknown-linux-gnu` passed, which confirms the target test code compiled; tests did not run. No hardware verification was performed. The confirmed timing and STM differences above remain open for implementation review.

## Independent re-review — launch timing and neighboring IOS/STM behavior

**Result: PASSED for the 1 ms timing and Wii target gate; IOS remains open.** Reviewer: `/root/reviewer_d`. Timing commits: `87b7f3f` and `4a75075`; target-gate fix is also recorded in the handoff above.

Rust's launch poll uses 60,750 ticks for 1 ms at 60.75 MHz, with the same checks and delay placement as C `udelay(1000)` (`crates/core/ogc-ios-sys/src/lib.rs:40–43, 100–110, 150–159`; `C-sources/libogc/libogc/ios.c:290–312`, `timesupp.c:66–77`). Both perform up to 401 IPC checks. The timing helper regression covers boundary and wraparound cases. The Wii-only target gate matches C's `HW_RVL` guard.

The remaining confirmed differences are broader than the timing change. C restores/unmasks the ACR handler before IPC reinitialization and the version query, while Rust reinitializes IPC and queries the version before restoring/unmasking (`ios.c:318–325`; Rust `ogc-ios-sys/src/lib.rs:142–174`). C STM initialization converts either open failure to success (`stm.c:87–92`), while Rust propagates negative open errors (`ios-sys/src/lib.rs:185–197`), which can change IOS startup error precedence. C successful STM init registers an event hook and close releases it (`stm.c:98–108, 123–153`); Rust's IOS path only opens and closes descriptors (`ios-sys/src/lib.rs:177–230`). Partial-open cleanup and close-error precedence also differ: Rust closes the immediate descriptor after second-open failure and retains failed-close descriptors; C leaves the immediate descriptor for shutdown and clears both descriptor fields even after close errors (`stm.c:87–120`; Rust `ios-sys/src/lib.rs:189–227`).

Cache invalidation before each Rust version poll remains a source difference from C's uninvalidated `read32`; the runtime effect remains uncertain. `cargo check -p ogc-ios -p ogc-ios-sys --target powerpc-unknown-linux-gnu --tests` passed and compiled target tests, which did not run. The relevant commit diff checks passed. No hardware verification was performed.

## 2026-10-05 fix handoff: share STM lifecycle with IOS startup

Implementer: `/root`. `ogc-ios-sys` now calls the same `ogc-stm` state used by the public STM API for initialization and shutdown. This removes duplicate STM descriptors, installs the real event-hook callback during IOS startup, and releases the hook before closing descriptors during IOS shutdown. The dependency cycle is removed by making `ogc-stm` read the Hollywood revision through the low-level `ogc-sys` accessor instead of the `ogc-system` wrapper. STM device opens now run in C order: eventhook is not opened if immediate open fails. Open errors propagate to IOS initialization, because returning success when required STM setup fails violates the repository's real implementation policy. Event-hook registration failure closes the descriptors and returns the ioctl error. Failed cleanup retains the descriptor in STM state so a later close can retry it.

Added PowerPC regression coverage for immediate-open short-circuit, returned open errors, event-hook failure cleanup, and descriptor retention after cleanup failure. `cargo check -p ogc-stm --tests --target powerpc-unknown-linux-gnu` and `cargo check -p ogc-ios-sys --tests --target powerpc-unknown-linux-gnu` passed; tests were compiled but not run. The `ogc-system-sys` library check passed. Its test target remains blocked by existing test-module errors; tests did not compile or run. Static review of the changed dependency graph and C ordering is needed. IOS timing/cache differences and the STM target-availability review remain open. No hardware verification was performed.
