# Tuxedo system compatibility review

Reviewer: `/root/reviewer_5`  
Implementer: none (first-pass review)  
Crate: `tuxedo-sys`  
C implementation: `../../C-sources/libogc/gc/tuxedo` and `../../C-sources/libogc/tuxedo`.

## Confirmed findings

1. **`KThread` is not C ABI-compatible.** C places `PPCContext ctx` first in `KThread`, followed by `next`, the state/suspend/priority fields, queue and wait/finish data, and `struct _reent r` (`../../C-sources/libogc/gc/tuxedo/thread.h:34-61`). The context is 0x2c0 bytes (`../../C-sources/libogc/gc/tuxedo/ppc/context.h:23-36`). Rust's public `KThread` contains only `state`, `suspend`, `prio`, `baseprio`, `token`, and `rc`, so its state starts at offset 0 (`crates/compatibility/tuxedo-sys/src/lib.rs:55-64`). Passing a C-allocated `KThread` to Rust therefore makes Rust write state over C's `ctx.pc`; the Rust type also cannot expose or preserve the remaining C fields. This prevents callers from treating the Rust `KThread` as the C structure.

2. **Queue wake and resume paths mark suspended or still-blocked threads running.** C's unblock path removes the thread from the queue but sets `KTHR_STATE_RUNNING` only when `!cur->suspend` (`../../C-sources/libogc/tuxedo/thread.c:253-285`). C resume decrements the suspend counter and returns without changing state when the thread remains suspended or still has a wait queue (`thread.c:99-120`). Rust unconditionally sets state to running after queue selection (`crates/compatibility/tuxedo-sys/src/lib.rs:511-520`) and after resume reaches suspend count zero (`lib.rs:364-376`), even when `THREAD_MAPS[index].wait_queue` is still non-null. The public state can therefore report a runnable thread while the LWP still keeps it blocked or suspended.

3. **Priority values above 127 are clamped instead of masked as in C.** C applies `prio & KTHR_MIN_PRIO` in both prepare and set-priority paths (`../../C-sources/libogc/tuxedo/thread.c:54-69,152-159`). Rust uses `min(KTHR_MIN_PRIO)` (`crates/compatibility/tuxedo-sys/src/lib.rs:320-324,399-409`). For example, input `0x80` becomes priority 0 in C and 127 in Rust; these values have opposite priority effects under C's convention where a smaller number is higher priority.

4. **Equal-priority queue wake order differs.** C inserts a waiter after existing equal-priority waiters and unblocks from the queue head (`../../C-sources/libogc/tuxedo/thread_priv.h:65-92`; `../../C-sources/libogc/tuxedo/thread.c:253-285`). Rust chooses the last matching map slot on an equal-priority tie because the comparison uses `<=` while scanning slots upward (`crates/compatibility/tuxedo-sys/src/lib.rs:481-510`). Map-slot order reflects allocation/reuse order, not queue insertion order, so a queue with equal-priority waiters can wake a different thread first.

5. **Zero-tick condition waits release and reacquire the mutex in Rust, while C returns immediately.** C returns `false` at the start of `KCondVarWaitTimeoutTicks` when `timeout_ticks == 0`, before modifying the mutex (`../../C-sources/libogc/tuxedo/sync.c:194-200`). Rust passes `Some(0)` to `lwp::cond_wait` (`crates/compatibility/tuxedo-sys/src/lib.rs:681-686`); the LWP path releases the mutex before setting the deadline and blocking (`crates/core/ogc-lwp-driver/src/runtime.rs:1512-1533`). This gives callers different mutex ownership and scheduling behavior for a zero timeout.

6. **Tick callbacks observe stale target values, and stop leaves the callback set.** C advances a periodic task's `target` before calling its callback, and clears `fn` before calling a one-shot task (`../../C-sources/libogc/tuxedo/tick.c:74-89`). Rust's timer engine advances its private deadline before invoking the adapter (`crates/core/ogc-lwp-driver/src/runtime.rs:751-768`), but the public `KTickTask.target` is advanced only after the callback returns (`crates/compatibility/tuxedo-sys/src/lib.rs:689-700`). A callback reading its task therefore sees the previous target in Rust. Rust's stop path clears `target` and `period` but leaves `fn_` set (`lib.rs:734-743`); C clears `fn` (`tick.c:115-132`). The public task state differs after callback and cancellation.

7. **The wrapper has fixed mapping limits absent from caller-owned C objects.** Rust stops preparing threads when its 32 `THREAD_MAPS` slots are full and stops mapping mutexes/condition variables after 64 `ObjectMap` entries (`crates/compatibility/tuxedo-sys/src/lib.rs:101-148,182-212,287-312`). These failures return silently or make lock/wait calls fail. C keeps `KThread` objects in a linked list and uses the caller's mutex/condition-variable memory directly (`../../C-sources/libogc/tuxedo/thread_priv.h:34-44,65-92`; `../../C-sources/libogc/tuxedo/sync.c:81-132,158-180`); it has no corresponding 32-thread or 64-object wrapper table limit.

8. **Mutex priority inheritance does not match C's transitive boost.** C inserts a blocked thread into the owner's waiter list, recalculates dynamic priority, and propagates that recalculation through the owner chain when necessary (`../../C-sources/libogc/tuxedo/sync.c:8-50,110-124`). Rust maps each `KMutex` to `lwp::mutex_lock` (`crates/compatibility/tuxedo-sys/src/lib.rs:215-225,596-611`); the LWP path boosts only the immediate owner (`crates/core/ogc-lwp-driver/src/runtime.rs:1401-1437`) and its recomputation scans only mutexes owned directly by one thread (`runtime.rs:813-829`). In a chain of threads blocked on owned mutexes, a high-priority waiter does not raise the ultimate owner to the same priority as C.

## Matching declarations and scoped differences

The checked public declarations `KThrQueue`, `KMutex`, `KRMutex`, `KCondVar`, `KTickTask`, and `PpcContext` preserve their C field order and corresponding 32-bit PowerPC field types (`../../C-sources/libogc/gc/tuxedo/thread.h:19-22`; `sync.h:9-20`; `tick.h:9-17`; `ppc/context.h:23-36`; Rust `lib.rs:29-99`). The Rust callback aliases use `extern "C"`, matching the C callback calling convention; this was introduced by commit `8864287`.

The Rust API also adds `k_thread_context_snapshot`, which returns a copy of the LWP snapshot (`crates/compatibility/tuxedo-sys/src/lib.rs:329-360`); there is no corresponding C API in the inspected Tuxedo headers. This is an additive Rust diagnostic, not a parity claim. The crate does not implement every inline/header facility from C, including `KThreadGetSelf`, `KThreadSleepUs/Ms`, `KMutexIsLockedByCurrentThread`, and the recursive-lock inline helpers. This review records those API-surface omissions but does not infer their intended use from the crate role.

### Fixed since the earlier review

- **Callback calling convention now matches C.** C declares `KThreadFn` and `KTickTaskFn` as C function pointers (`../../C-sources/libogc/gc/tuxedo/thread.h:32`; `gc/tuxedo/tick.h:9-17`). Rust aliases now use `unsafe extern "C" fn` (`crates/compatibility/tuxedo-sys/src/lib.rs:26-27`), introduced by `8864287`.
- **The PowerPC context type now matches C layout, but `KThread` still does not.** C's `PpcContext` is the first field of `KThread` (`gc/tuxedo/thread.h:34-36`) and is 0x2c0 bytes (`gc/tuxedo/ppc/context.h:23-36`). Rust now declares a `PpcContext` with matching offsets and size assertions (`lib.rs:29-53`, from `c7914a1`), but Rust `KThread` still contains only the state fields and result (`lib.rs:55-64`); it does not embed `PpcContext`, `next`, `waiters`, the wait/finish union, or `_reent r`. The `KThread` ABI mismatch and incorrect offsets therefore remain.
- **Prepared-thread initial state now matches.** C `KThreadPrepare` sets `state = KTHR_STATE_WAITING`, `suspend = 1`, masks the priority, and initializes base priority (`../../C-sources/libogc/tuxedo/thread.c:54-69`). Rust now sets the same WAITING state and suspend count (`crates/compatibility/tuxedo-sys/src/lib.rs:320-325`), fixing the earlier UNINIT state difference in `01a9865`. The priority masking mismatch remains as described below.
- **Zero-tick condition waits no longer release/reacquire the mutex.** C returns `false` before changing mutex state when `timeout_ticks == 0` (`../../C-sources/libogc/tuxedo/sync.c:194-200`). Rust still calls `lwp::cond_wait(..., Some(0))` (`crates/compatibility/tuxedo-sys/src/lib.rs:656-686`), but the current LWP implementation checks zero before `release_mutex_locked` and returns timed out (`crates/core/ogc-lwp-driver/src/runtime.rs:1514-1531`; added by `e10a965`). The prior mutex ownership/scheduling finding is fixed at the current source. This check compiles but has no Tuxedo-specific regression test asserting mutex ownership for zero timeout.

### Findings still present

- **Queue unblock and resume can mark a blocked or suspended thread RUNNING.** C queue unblock sets RUNNING only for an unsuspended thread (`../../C-sources/libogc/tuxedo/thread.c:253-285`), and C resume leaves state unchanged if suspension remains or `wait.queue` is set (`thread.c:99-120`). Rust `unblock_queue` unconditionally writes RUNNING before waking (`crates/compatibility/tuxedo-sys/src/lib.rs:481-524`), while `k_thread_resume` writes RUNNING once its wrapper suspend count reaches zero without checking `THREAD_MAPS[index].wait_queue` (`lib.rs:364-378`).
- **Priority values are clamped instead of masked.** C uses `prio & KTHR_MIN_PRIO` in prepare and set-priority (`../../C-sources/libogc/tuxedo/thread.c:54-69,152-159`). Rust uses `min(KTHR_MIN_PRIO)` in both paths (`crates/compatibility/tuxedo-sys/src/lib.rs:287-327,399-410`). For input `0x80`, C stores 0 while Rust stores 127.
- **Equal-priority waiter order differs.** C inserts after existing equal-priority threads (`../../C-sources/libogc/tuxedo/thread_priv.h:65-92`) and removes from the queue head (`thread.c:253-285`). Rust scans fixed mapping slots and replaces an equal-priority selection on `<=` (`crates/compatibility/tuxedo-sys/src/lib.rs:481-510`); the last matching slot can be selected regardless of actual queue insertion order.
- **Tick callback-visible task state still differs.** C advances a periodic task's `target` before calling the callback and clears a one-shot task's `fn` before its callback (`../../C-sources/libogc/tuxedo/tick.c:74-89`), and stop clears `fn` (`tick.c:115-132`). Rust calls the callback before advancing public `KTickTask.target` and does not clear `fn_` on stop (`crates/compatibility/tuxedo-sys/src/lib.rs:689-700,734-743`).
- **Rust has fixed thread and sync-object mapping capacities.** The adapter returns early when its 32 `THREAD_MAPS` slots or 64 mutex/condition mapping slots are exhausted (`crates/compatibility/tuxedo-sys/src/lib.rs:101-102,182-212,287-312`). C keeps threads in its linked list and uses caller-owned sync objects directly (`../../C-sources/libogc/tuxedo/thread_priv.h:34-44,65-92`; `sync.c:81-132,158-180`), without these wrapper mapping limits.
- **Priority inheritance still stops at the immediate mutex owner.** C `KThreadUpdateDynamicPrio` reorders the blocked thread in its wait queue and walks from a mutex waiter to that mutex's owner (`../../C-sources/libogc/tuxedo/sync.c:8-50`), called when adding a waiter (`sync.c:110-124`). Rust `mutex_lock` raises only the current mutex owner (`crates/core/ogc-lwp-driver/src/runtime.rs:1437-1444`). `recompute_priority_locked` scans mutexes owned by that one thread but does not continue along the thread's own wait chain (`runtime.rs:826-842`). A high-priority waiter therefore does not boost the ultimate owner through a multi-mutex chain as C does.

## Independent re-review: equal-priority waiter FIFO

Result: **NEEDS_CHANGES** for full C parity. Reviewer: `/root/reviewer_b`. Implementer: `/root/worker_b`. Implementation commit: `a99dd96` (`Preserve FIFO for equal priority waiters`); handoff: `fba5fab`. I inspected the complete implementation diff, current Rust queue operations, the C queue insertion/unblock code, and the adjacent C priority-update path.

### FIFO behavior that passed

For waiters whose priority does not change while they wait, the fix matches C's equal-priority ordering. C's `KThrQueueGetInsertPosition` advances past existing entries whose priority is `<=` the new thread's priority, so a new equal-priority waiter is inserted after existing waiters (`../../C-sources/libogc/tuxedo/thread_priv.h:65-92`). `KThrQueueUnblockCommon` then removes matching waiters from the head in that order (`../../C-sources/libogc/tuxedo/thread.c:253-285`). Rust now assigns a fresh `wait_order` at each `k_thr_queue_block`, selects by priority and then oldest order in `unblock_queue`, and uses the same tie-break when rebuilding the exposed queue bounds (`crates/compatibility/tuxedo-sys/src/lib.rs:243-297,490-560`). Reuse of a lower map slot no longer makes a later waiter overtake an older equal-priority waiter.

### Remaining mismatch

The ticket records the original enqueue time, but C can reinsert a waiter when its priority changes. `KThreadSetPrio` calls `KThreadUpdateDynamicPrio`; when the effective priority changes, that function removes and reinserts the thread in its wait queue (`../../C-sources/libogc/tuxedo/thread.c:152-159`; `../../C-sources/libogc/tuxedo/sync.c:8-48`). That insertion order determines its position among any newly equal-priority waiters. Rust `k_thread_set_prio` updates the mapped object's priority and LWP priority but does not refresh the Tuxedo queue bounds or assign a new queue-order ticket (`crates/compatibility/tuxedo-sys/src/lib.rs:436-449`). `unblock_queue` will select by the new priority but still use the old `wait_order` for ties, so a waiter whose priority changed can wake in a different order from C. The added regression tests call only `consider_waiter` with preassigned tuples and test ticket wrap; they do not cover changing a blocked waiter's priority or compare the resulting order with C's requeue behavior (`lib.rs:803-827`).

The slot-reuse and wrap tests therefore support the ordinary FIFO correction, but do not establish parity across the priority-update path. Other Tuxedo findings recorded above remain open. This result does not mark `tuxedo-sys` complete.

## 2026-10-06 dynamic shared timer storage

The shared LWP timer engine used by `KTickTask` is now workspace-backed and has no fixed 64-entry timer table. Active timer nodes are intrusive and completed/cancelled nodes are recycled, so Tuxedo task registration is limited by the LWP workspace rather than an arbitrary timer count. No allocator operation is performed when a one-shot timer completes in decrementer context. ## 2026-10-06 KThread ABI, intrusive synchronization, and compatibility completion pass

The previously recorded structural Tuxedo blockers are closed at source level. `KThread` now follows the C field order and 32-bit layout: the 0x2c0 `PPCContext`, global-list link, state/suspend/priorities, waiter queue, wait/finish union, and 512-byte newlib `_reent` are all present. Compile-time offset/size assertions cover the PowerPC ABI layout.

The fixed 32-entry thread map and 64-entry mutex/condition maps were removed rather than enlarged. Threads use the public intrusive links from `KThread`; object-to-LWP lookup uses the driver's live argument registry. Mutex ownership is stored directly in `KMutex.owner`, mutex waiters use the owner's `KThread.waiters`, and condition variables use the same shared intrusive queue/key model as C. Priority inheritance follows the owner chain and queue reinsertion uses the same priority/FIFO ordering rules.

The public `KThread.ctx` is now updated at the scheduler's actual context-save points. Cooperative switches copy the just-saved 176-word context before the next context is loaded, and interrupt-return saves mirror the exception context immediately. The mirror is stored as a raw byte pointer and Rust snapshots use unaligned reads, so the implementation does not impose the driver's internal 32-byte `Context` alignment on the C-layout `KThread.ctx`. The public embedded `_reent` is registered as the running thread's authoritative newlib storage rather than remaining an initialized but disconnected copy.

The remaining inline/header facilities are also represented through shared Rust primitives: current-thread lookup, microsecond/millisecond sleep conversion, current-owner mutex query, recursive mutex lock/try/unlock, and nanosecond/microsecond/millisecond condition waits. The legacy `KrMutex` Rust spelling remains available and `KRMutex` is provided as the C-header-compatible alias.

Intentional safety differences are retained and documented: invalid mutex ownership is rejected rather than spinning forever, recursive unlock at count zero is ignored rather than underflowing, null/invalid object pointers are checked where C would dereference them, and live LWP handles are validated before mapping them back to caller-owned objects.

One confirmed non-safety blocker remains after this pass: `KThread.ctx` is a saved-state mirror, not the scheduler's authoritative restore source. C restores directly from the caller-owned `KThread.ctx`, so a caller may edit a suspended thread's saved context before resume; Rust currently restores from its private scheduler context and would ignore such edits. This is an observable ABI/state difference and keeps `tuxedo-sys` at `parity_blocked`.

All other named structural findings in this tranche are closed at source level: the embedded `_reent` is authoritative, fixed thread/mutex/condition maps are gone, queues are intrusive, the dynamic-capacity limits are removed, and the checked inline/header compatibility helpers are present.


## 2026-10-06 authoritative KThread context restore

The final named Tuxedo structural blocker is closed at source level. C restores a selected thread directly from `KThread.ctx` in both ordinary `KThreadSwitchTo` and interrupt-return context changes (`../../C-sources/libogc/tuxedo/thread.c:83-96`; `../../C-sources/libogc/tuxedo/interrupt_asm.S:48-103`). The shared Rust LWP scheduler now uses caller-owned context storage as the authoritative restore source whenever a thread has registered a context mirror. Immediately before either a cooperative restore or an interrupt-return restore, it copies the caller-owned bytes into the driver's aligned private `Context` and restores from that aligned copy. A caller edit to a suspended `KThread.ctx` therefore affects the resumed register state as it does in C.

The copy is byte-based. It does not create a Rust `Context` reference to the caller-owned object and therefore does not impose the driver's 32-byte internal alignment on the C-layout field. Save behavior remains unchanged: cooperative and interrupt saves first update the driver's private context and then mirror the saved bytes back to `KThread.ctx`. The same centralized restore helper is used by both restore paths. Because a prepared Tuxedo thread now starts directly from its public context, the Rust `k_thread_exit` target stored in LR uses the C ABI, matching C's `KThreadExit` return path.

A focused regression exercises an intentionally non-`Context`-aligned, four-byte-aligned caller buffer and verifies that edited PC, LR, GPR, and GQR fields are consumed into the aligned restore context.
